## 1. Schema Strategy & Database Security
All changes must be non-destructive, additive, and backward-compatible. Existing data in `tenants`, `users`, `accounts`, `leads`, `opportunities`, and vertical tables must remain intact.

---

## 2. PostgreSQL Row-Level Security (RLS) Evaluation

Section 2 of `Strong_Isolation.md` mandates evaluating PostgreSQL Row-Level Security (RLS) as an additional defense-in-depth enforcement layer.

### 2.1 RLS Evaluation Findings
- **Benefits**:
  - Provides database-engine-level enforcement against inadvertent omission of `.filter(Model.tenant_id == current_tenant.id)` in application code.
  - Guarantees that even if an application bug exists, PostgreSQL will reject cross-tenant rows at the query execution level.
- **Implementation Design**:
  - Application sets session-level configuration variable on each transaction:
    `SET LOCAL app.current_tenant = '<tenant_uuid>';`
  - Table policy:
    ```sql
    CREATE POLICY tenant_isolation_policy ON accounts
      USING (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid);
    ```
  - **Connection Pooling & Non-Superuser Constraints**:
    - Application connection pool user (`salesfortis`) must NOT be a superuser (superusers bypass RLS).
    - `SET LOCAL` is transaction-scoped, ensuring pooled connections never bleed tenant context into subsequent queries.
- **Rollout Strategy**:
  - Phase 1: Enforce strong application-level tenant scoping with server-side dependencies and negative test cases.
  - Phase 2: Add RLS policies incrementally on high-sensitivity tables (`tenants`, `accounts`, `consent_evidences`, `sov_applications`) using separate migration/admin database roles.

## 3. Database Ownership & Foreign Key Invariants

1. **Foreign Key Tenant Scoping**:
   - Every vertical entity (`sov_applications`, `consent_evidences`, `rate_cards`, etc.) declares a foreign key to `tenants.id`.
   - In cross-entity joins (e.g. `SOVApplication` joining `Project`), the child record must have the same `tenant_id` as the parent record.
2. **Zero Cross-Module Direct Writes**:
   - Modules write only to their owned tables. Cross-module data linkages (such as linking a Construction RFQ to a core CRM Account) are read-only references via foreign keys.

## 4. Planned Non-Destructive Schema Additions (Phase 1)

### 4.1 `Tenant` Model Enhancement (`core/models/auth.py`)
- **Column**: `industry`
  - **Type**: `sa.String()`
  - **Default**: `"all"` (Allows existing tenants full access, while newly registered tenants get strictly assigned `"construction"`, `"clinical"`, or `"maritime"`).
  - **Nullable**: `True` (Ensures zero breaking changes for existing tenant rows).

### 4.2 Migration Script Execution Plan
```python
def upgrade():
    op.add_column('tenants', sa.Column('industry', sa.String(), nullable=True, server_default='all'))

def downgrade():
    op.drop_column('tenants', 'industry')
```
- Migration will be autogenerated and verified before applying with `alembic upgrade head`.
